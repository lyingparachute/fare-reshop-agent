# Reshop review

Status: active - 01 in progress; 02 ready; 03 ready, real recording needs the owner's key; 04 blocked, needs the two recordings and Q2

## Why this feature exists

A ticket bought weeks ago often costs less today. Rebooking pays off only when the price drop beats the change fee on the old ticket and the new fare takes nothing away from the traveler. This feature reads booked flights and fares on sale, and gives a person one recommendation per booking: rebook or keep, which offer, the nominal saving, and why. Plain code owns every number and rule. A language model looks only at bookings where a rebooking could make sense: it reads the facts through tools, picks an offer or says keep, and writes the rationale. A safety check re-runs the rules on its choice. Nothing is ever booked automatically.

The repo has no code yet. The sample data lives in `fixtures/pnrs.json` (5 bookings) and `fixtures/fares_feed.json` (6 offers, captured 2026-07-08T09:00:00Z). A second, made-up data set, `fixtures/scenarios/` (6 bookings, 7 offers), holds the judgment cases: a model choice that is not the highest saving, a model keep, a failed refundability rule, a seat-contention pair and a seats failure (D34). The real fixtures are never edited. All five departures are between 2026-08-15 and 2026-10-10, after the capture time.

## Capabilities, stories and walkthroughs

Capabilities: review all bookings offline with rules only; review with a live model; replay a recorded model run offline; record a run; swap the exchange-rate source; read why each result came out the way it did.

### S1 - Rules-only review

As a travel agent, I want one recommendation per booking with the chosen offer, the nominal saving and the rules each offer passed or failed, so that I can decide which bookings to look at without re-checking fares by hand.

Walkthrough:

1. The agent runs `uv run fare-reshop review --model none`. First use: uv creates the environment on the first run. `--data scenarios` runs the made-up scenario set instead of the sample (D34); the default is `sample`.
2. The tool loads the data snapshot (bookings, offers and capture time), the policy file and the exchange-rate file. Error: a missing or unreadable file stops the run with the path and the reason, exit code 2. Error: a booking record with a missing or wrong field, a multi-segment itinerary, a `totalPaid` that does not equal passengers times price, or a departure before the capture time becomes a result with status `INVALID_DATA` and the reason; the other bookings still run. Error: a booking whose currency has no exchange rate from the minimum saving's currency (USD) becomes `INVALID_DATA` with "no exchange rate from USD to <currency>". Error: a bad offer record, or every copy of a duplicated offer id, is left out and listed under `data_issues` with the offer id and the reason; a duplicated booking reference keeps the first record and lists the rest. Money is read as text into `Decimal`, never through a float, and unknown keys fail parsing, except the documented top-level `_comment`. Empty: no bookings prints an empty result list and exit code 0.
3. For each booking, every offer with the same origin, destination and departure date is evaluated: each rule gives PASS or FAIL with a reason, and the nominal saving is computed in the booking's currency. An offer in the booking's currency needs no rate. Error: an offer in another currency with no rate to the booking's currency fails the rule `exchange_rate`. Empty: no offers on the route gives `KEEP` with "no offers on this route and date".
4. An offer is eligible when it passes every rule and its rounded saving meets the minimum. The minimum is 50 USD, converted to the booking's currency with the same exchange-rate port and rounded once. No eligible offer gives `KEEP`, with every offer's evaluation. At least one eligible offer: in `none` mode the code picks the eligible offer with the highest saving (ties broken by offer id) and returns `REBOOK` with `decided_by: rules`, `confidence: null` and a rationale built from the rule results.
5. Output is JSON on stdout with a `schema_version`. `--format table` prints an aligned table for people, in color when the terminal supports it and plain when `NO_COLOR` is set or output is piped.

### S2 - Review with a live model

As a travel agent, I want the bookings worth a second look reviewed by a model that weighs the trade-offs and writes a short rationale, so that each recommendation explains itself in plain words.

Walkthrough:

1. The agent copies `.env.example` to `.env.local` and sets `OPENAI_API_KEY`. Error: the `live` extra is not installed; exit code 2 with "run uv sync --extra live". Error: no key or an empty key; exit code 2 with "OPENAI_API_KEY is not set", before any call.
2. The agent runs `uv run --env-file .env.local fare-reshop review --model openai`.
3. Bookings with no eligible offer are settled by code as in S1, with no model call.
4. For each other booking the model gets a first message naming the booking, then calls tools: `get_booking`, `search_offers`, `check_offer`. Error: a bad tool argument or an unknown offer id goes back to the model as a tool error with a hint. Error: the same call twice in a row, or 10 turns without a final answer, ends that booking with `INCOMPLETE_ANALYSIS`. Error: the provider fails (network, timeout, rate limit, server error); that booking gets `INCOMPLETE_ANALYSIS` with `incomplete_reason: provider_error`, and the others continue. A refusal is a final step, not a provider failure: `INCOMPLETE_ANALYSIS` with `incomplete_reason: refusal`.
5. The model returns rebook with an offer id, or keep, plus a rationale and a confidence. The safety check re-runs the rules and the money math. Error: the chosen offer is not on the route, fails a rule or misses the minimum; `NEEDS_REVIEW` with the reason. Keep while an eligible offer exists: `NEEDS_REVIEW` with "model and rules disagree" and the model's rationale, so a person sees both sides.
6. Output as in S1, with `decided_by: model`, the tool trace, the turn count and token usage per booking. When the model's valid choice is not the highest saving, `best_offer_id` names the one that is.

### S3 - Offline replay of a recorded run

As anyone who clones the repo, I want the default run to replay a recorded model run with no key and no network, so that I see real model behavior for free.

Walkthrough:

1. The user runs `uv run fare-reshop review`. The default mode is `recorded` and reads the recording of the chosen data set: `recordings/review-run.json` for `sample`, `recordings/scenarios-run.json` for `scenarios` (D22). Error: the file is missing; exit code 2 with "no recording found: run with --model none, or record one with --model openai --record".
2. The real loop runs. Tools run against the fixtures; only the model's turns come from the file.
3. Error, all exit code 3 with `StaleRecording`, the booking and the turn: the data snapshot, policy or rates changed since recording; a turn's digest differs from the recorded one; a booking needs a model turn the file does not have; a booking finished with recorded turns left over. The message ends with "re-record with --model openai --record".
4. Output is the same shape as S2, with `mode: recorded`. Bookings settled by rules need no turns and are not in the file. The trace shows `recorded_model` and `recorded_usage`, the model and token usage at recording time.

### S4 - Record a run

As the maintainer, I want to record one live run into a file, so that the offline replay shows what the real model did.

Walkthrough:

1. The maintainer runs `uv run --env-file .env.local fare-reshop review --model openai --record`.
2. Turns are kept in memory as the run goes. Each holds the digest of what the model saw, the step it returned and its token usage. No key, request ids or headers are kept.
3. Success means no provider failure happened. Bookings that ended on a loop limit or a refusal still count as recorded, and replay reproduces them. Then the file is written atomically (write to a temporary file, then rename), replacing the old one, and the path is printed.
4. Error: any provider failure in the run; nothing is written, the old recording stays, exit code 2 with the booking and the error.

### S5 - Swap the exchange-rate source

As a developer, I want exchange rates behind one interface, so that a live rate source is one new adapter and nothing else changes.

Walkthrough:

1. The developer writes a class that satisfies the `ExchangeRates` port and wires it in `composition/`. Nothing in `domain/` or `orchestration/` changes.
2. Error: the source has no rate for a pair; the offer fails the rule `exchange_rate` (S1 step 3).
3. Each converted amount in the output shows the rate, its direction ("1 EUR = 1.1433 USD") and the date of the rate data. The rate sits on the offer evaluation that used it.
4. Changing the rates changes tool results, so an existing recording goes stale and must be re-recorded (S3 step 3).

### S6 - Understand the design

As an engineer judging the approach, I want a design document that says where the model is trusted and where it is not, so that I can judge the design without reading all the code.

Walkthrough:

1. The reader opens `README.md`: what it does, how to run each mode, sample output.
2. The reader opens `DESIGN.md`: architecture, the model boundary, money safety, the output contract, scale and cost, data handling, assumptions and open questions, what was left out, the AI-usage note, the documented limits (D35) and a link to `docs/future-work.md`. A scenario walkthrough shows the model's judgment and the safety check on one booking.
3. `GLOSSARY.md` and `docs/adr/` hold the terms and the hard-to-reverse decisions.

### S7 - First run on a fresh machine

As a programmer who has never seen this repo or its tools, I want every missing piece named with the exact command that fixes it, so that I get from clone to a result without guessing.

Walkthrough:

1. The reader runs `./start.sh`. It checks for `uv`. Missing: it says what uv is, prints the official install command, and asks "Install uv now? [y/N]". Only `y` runs it. Anything else stops with the manual command. Nothing is ever installed without that answer.
2. It runs `uv sync` after asking the same way, then `fare-reshop doctor`, then the default review.
3. `fare-reshop doctor` prints one line per check with a mark and, for each failure, the command that fixes it: Python version, installed packages, the `live` extra, `OPENAI_API_KEY` set (never its value), the recording present and matching the data, and the fixture and config files readable. Exit code 0 when everything the default run needs is present.
4. Every CLI error has the same three lines: what went wrong, why, and the command that fixes it. No traceback unless `--debug` is passed.
5. Windows: `./start.sh` needs a POSIX shell; the README gives the same steps as uv commands.
